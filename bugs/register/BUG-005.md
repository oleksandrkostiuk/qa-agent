# BUG-005: Duplicate username registration accepted instead of rejected

**Test Case:** TC-REGISTER-USERNAME-006
**Feature:** register
**Flow:** username-availability
**Priority:** High
**Severity:** High
**Date Found:** 2026-10-05
**Source Report:** reports/register-2026-10-05-143606

## Description
`POST /api/user/` accepts a registration whose `userName` ("test") already exists on the instance, returning `200 OK` instead of rejecting it (e.g. `400`/`409`). Server-side username-uniqueness enforcement does not appear to be implemented — a client that bypasses the UI's client-side availability check can register a duplicate username outright. This may share the same root cause as BUG-004 (TC-REGISTER-POSTLOGIN-002), where registration responses look successful but don't translate into a real persisted user record.

## Steps to Reproduce
1. Send `POST /api/user/` directly (bypassing the UI's client-side availability check) with `userName` "test" (an already-existing username) and otherwise valid data.

## Expected Result
Server should reject the duplicate username registration (e.g. 400/409) - this is the intended/correct behavior being asserted. NOTE: this case currently FAILS against the live app, which returns 200 OK and accepts the request despite the duplicate username; server-side uniqueness enforcement is not implemented. This is a known product gap (see explorer-output/register.md GAPS FOUND) - the test documents the bug rather than being skipped.

## Actual Result
Attempt 1: status 200, empty body (duplicate username accepted, not rejected). Retry: status 200 again, empty body — same result both times.

## Request/Response
Request: POST /api/user/
Headers: { "Content-Type": "application/json" }
Body: { "firstName": "QA", "lastName": "Tester", "userName": "test", "password": "Passw0rd1", "confirmPassword": "Passw0rd1", "gender": "Male" }

Response: 200
Body: (empty)
